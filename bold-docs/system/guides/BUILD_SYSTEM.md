# Build System Specification

## Purpose

This document specifies how the site is installed, developed, validated, built, analyzed, and prepared for deployment. It is a source-of-truth guide for contributors who need to understand the workspace build contract without reverse-engineering scripts and configuration files.

## Scope

The build system covers:

- Local dependency installation and runtime requirements.
- Workspace orchestration from the repository root.
- Production builds for the demo application.
- Library builds for internal packages.
- Static data synchronization.
- Type checking, linting, formatting, tests, coverage, and bundle analysis.
- Deployment artifact generation for static hosting.

The build system does not automatically refresh remote data during a normal production build. Data refresh is an explicit command so builds remain deterministic from committed source.

## Runtime Contract

The repository is an npm workspace managed from the repository root.

| Requirement | Value |
|---|---|
| Package manager | npm `12.0.2` |
| Node.js | `>=26.0.0` |
| Workspace runner | Turborepo |
| Application bundler | Vite |
| Language compiler | TypeScript |
| Linter | Oxlint |
| Test runner | Vitest |
| Formatter | Prettier |

All root commands assume dependencies have been installed with `npm ci`.

## Workspace Layout

The repository is organized as a small monorepo:

| Path | Role |
|---|---|
| `apps/demo-app` | Browser application and static site entry point. |
| `packages/ui-components` | Shared React component package built as a library. |
| `packages/design-tokens` | Shared static package with a placeholder build step. |
| `scripts` | Repository-level build helpers, including metadata generation. |
| `dist` | Production deployment output generated by the demo app build. |
| `reports` | Optional analysis output. |

The root workspace does not emit production browser assets directly. It delegates work to package scripts through Turborepo.

## Root Commands

Run these commands from the repository root.

| Command | Purpose |
|---|---|
| `npm run build` | Runs the full Turborepo build graph. |
| `npm run build:deploy` | Builds only the deployable demo application and its dependencies. |
| `npm run build:ci` | Runs the expected CI build sequence for internal packages and the demo application. |
| `npm run dev` | Starts persistent development tasks through Turborepo. |
| `npm run preview` | Serves the built demo application locally through the app workspace. |
| `npm run sync:data` | Refreshes committed static JSON snapshots used by the demo application. |
| `npm run lint` | Runs Oxlint across participating workspaces. |
| `npm run type-check` | Runs TypeScript validation across participating workspaces. |
| `npm run test` | Runs test suites through Turborepo. |
| `npm run test:coverage` | Runs coverage-enabled test suites through Turborepo. |
| `npm run format` | Applies Prettier formatting to supported files. |
| `npm run format:check` | Checks formatting without modifying files. |
| `npm run clean` | Removes generated outputs declared by workspace clean scripts. |

## Build Graph

Turborepo owns task ordering and cache boundaries.

The standard `build` task depends on upstream workspace builds through `^build`. This ensures packages are built before consumers that import them.

The demo app build is scoped as `@tailwindspark/demo-app#build` in `turbo.json`. It depends on upstream builds and declares `../../dist/**` as its output because the deployable site is emitted at the repository root.

The UI component package emits `dist/**` from its own package directory. The static design package has a no-output build task and is still part of the graph so dependent packages can rely on a consistent workspace contract.

Validation tasks are also graph-aware:

- `lint` depends on upstream `build`.
- `type-check` depends on upstream `build`.
- `test` depends on upstream `build`.
- `test:coverage` depends on upstream `build` and emits `coverage/**`.

Persistent tasks such as `dev` and `test:ui` are not cached.

## Demo Application Build

The demo application build script is:

```powershell
npm --workspace @tailwindspark/demo-app run build
```

Internally, the app runs:

```powershell
tsc -b && vite build
```

The TypeScript project build runs first. If type compilation fails, Vite does not run. Vite then bundles the browser application and writes the static site to:

```text
dist/
```

The output directory is emptied before each app production build.

## Base URL

The app base URL is controlled by `VITE_BASE_URL`.

| Mode | Base URL behavior |
|---|---|
| Production without `VITE_BASE_URL` | Uses `/TailwindSpark/`. |
| Production with `VITE_BASE_URL` | Uses the provided environment value. |
| Non-production | Uses `/`. |

The default production base URL supports project-page hosting where the site is served from a repository path instead of a domain root.

## Asset Output

Production assets are emitted with stable content hashes.

| Asset type | Output pattern |
|---|---|
| JavaScript entries | `assets/js/[name]-[hash].js` |
| JavaScript chunks | `assets/js/[name]-[hash].js` |
| Images | `assets/images/[name]-[hash][extname]` |
| Fonts | `assets/fonts/[name]-[hash][extname]` |
| Stylesheets | `assets/styles/[name]-[hash][extname]` |
| Other assets | `assets/[name]-[hash][extname]` |

CSS code splitting is enabled. Small assets up to 8192 bytes may be inlined by Vite.

## Bundle Splitting

The app uses manual Rollup chunking to keep large dependency groups and route-level code paths separated.

Chunk groups include:

- Core React framework dependencies.
- Real-time communication dependencies.
- Mapping dependencies.
- Markdown rendering dependencies.
- Icon dependencies.
- General third-party dependencies.
- Page modules.
- Shared component modules.
- Utility modules.

This chunking strategy is intended to improve browser cache behavior and keep route-specific code isolated from shared runtime code.

## Build Targets

The production build targets modern browsers and ES2020-compatible JavaScript:

- `es2020`
- `edge88`
- `firefox78`
- `chrome87`
- `safari15`

Minification is handled by esbuild. Source maps are disabled for normal production builds. Compressed bundle size reporting is enabled.

The chunk size warning limit is 400 KiB.

## Build Constants

The Vite build defines these compile-time constants:

| Constant | Value |
|---|---|
| `__BUILD_DATE__` | ISO timestamp generated when Vite config is evaluated. |
| `__BUILD_VERSION__` | App package version from the demo app package manifest. |

Application code may use these constants for metadata and diagnostics.

## Post-Build Metadata

After the demo app build finishes, the app runs:

```powershell
tsx ../../scripts/generate-meta.ts ../../dist
```

This script generates static metadata files in the deployment output directory. The deployment artifact is not considered complete until this post-build step succeeds.

## UI Component Library Build

The UI component package build script is:

```powershell
npm --workspace @tailwindspark/ui-components run build
```

Internally, the package runs:

```powershell
tsc -p tsconfig.build.json && vite build
```

The TypeScript build emits declaration files and validates the package build configuration. Vite then emits library bundles in ES module and UMD formats.

The library build treats React runtime packages as externals. Consumers are expected to provide React rather than bundling duplicate React copies into the library output.

## Static Package Build

The static package participates in the workspace graph with a lightweight build command:

```powershell
npm --workspace @tailwindspark/design-tokens run build
```

The command currently confirms the package build step without generating files. Keeping this workspace in the graph preserves a stable package contract for consumers and CI.

## Development Server

The root development command is:

```powershell
npm run dev
```

This delegates to Turborepo and starts persistent workspace dev tasks.

The demo application dev server is Vite. Its development configuration includes:

- Local API proxy routes for selected JSON endpoints.
- Security-related response headers.
- Filesystem access configured for the monorepo development layout.

The dev server is for local iteration only and does not produce deployment artifacts.

## Static Data Synchronization

The data synchronization command is:

```powershell
npm run sync:data
```

The root command delegates to the demo application workspace, which runs these scripts in sequence:

```powershell
node scripts/sync-projects-data.mjs
node scripts/sync-repos-data.mjs
node scripts/sync-articles-data.mjs
```

These scripts refresh committed static JSON snapshots consumed by the app. Because they reach remote sources, they are intentionally separate from `npm run build`.

Expected workflow:

1. Run `npm run sync:data` only when the committed snapshots should be refreshed.
2. Review the generated JSON diffs.
3. Run validation and build commands after accepting the data changes.

## Bundle Analysis

Bundle analysis is opt-in and does not run during normal builds.

Run:

```powershell
npm --workspace @tailwindspark/demo-app run build:analyze
```

The analysis build uses Vite analyze mode and writes an HTML report to:

```text
reports/bundle-analysis.html
```

The report is intended for local inspection when dependency size, chunk boundaries, or asset growth need review.

## Validation Gates

Use this validation sequence before treating build-system changes as complete:

```powershell
npm ci
npm run lint
npm run type-check
npm run test:coverage
npm run build
git diff --check
```

For documentation-only changes, `npm run build` and `git diff --check` are usually sufficient unless the documentation change also updates scripts, package manifests, TypeScript configuration, or Vite configuration.

## Deployment Artifact

The deployable site is the repository-root `dist` directory generated by the demo application production build.

A valid deployment artifact must include:

- HTML entry files.
- Hashed JavaScript bundles.
- Hashed stylesheet assets.
- Static image, font, and miscellaneous assets.
- Post-build metadata generated by the repository metadata script.
- Any static data snapshots required by the application at runtime.

The artifact is static and does not require a Node.js server at runtime.

## CI Expectations

Continuous integration should:

1. Install dependencies with `npm ci`.
2. Use Node.js 26 or newer.
3. Run linting.
4. Run type checking.
5. Run tests or coverage according to the workflow tier.
6. Run the deploy build.
7. Upload or publish the generated `dist` directory.

CI should not refresh remote data unless the workflow is explicitly intended to update committed data snapshots.

## Failure Handling

Common failure categories:

| Failure | Likely source | Expected response |
|---|---|---|
| Dependency install failure | Node/npm version mismatch or lockfile drift | Verify Node.js 26+, npm 12.0.2, then rerun `npm ci`. |
| TypeScript failure | Broken type contract or project reference issue | Fix TypeScript errors before rerunning Vite. |
| Lint failure | Oxlint rule violation | Fix the reported source issue or adjust the rule only with clear justification. |
| Test failure | Behavior regression or stale assertion | Fix implementation or update the test when the expected behavior intentionally changed. |
| Build failure | Vite config, import resolution, asset, or dependency issue | Fix the root error and rerun `npm run build`. |
| Metadata failure | Post-build script or invalid output path | Fix the metadata script or verify the `dist` path exists. |
| Deployment path issue | Incorrect base URL | Set or verify `VITE_BASE_URL` for the target hosting path. |

## Change Control

Changes to build scripts, `turbo.json`, Vite configuration, TypeScript configuration, package manifests, or deployment workflows should be treated as build-system changes.

Build-system changes should include:

- A short rationale for the change.
- Updated documentation when behavior changes.
- Validation output from the affected gates.
- Confirmation that generated artifacts are either intentionally committed or intentionally ignored.

## Invariants

These rules should remain true unless the build system is intentionally redesigned:

- Root commands orchestrate workspace tasks through Turborepo.
- The demo application production build emits to repository-root `dist`.
- A normal production build does not refresh remote static data.
- The app build fails on TypeScript errors before bundling.
- The deployable output is static and can be hosted without a runtime server.
- Bundle analysis remains opt-in.
- Build outputs and coverage outputs are declared in Turborepo for cache correctness.
